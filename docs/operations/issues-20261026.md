## Prerrequisitos de entrega

1. Node >=22.12 <23. Ejecutar `npm ci` y `npm run qa:isolated`. El deploy de Actions depende de esta bateria y solo corre desde main.
2. Preparar respaldo y ventana de escritores detenidos para la migracion de codigos. Elegir expresamente la base autorizada mediante el cargador de entorno habitual; el operador no cambia automaticamente a una base QA.
3. Ejecutar `node scripts/migrations/patient-code-counter.js` para preflight de solo lectura. Duplicados bloquean; revisar sin renumerar pacientes automaticamente. Con escritores ya detenidos: `node scripts/migrations/patient-code-counter.js --apply --writers-stopped`. El segundo flag es una declaracion del operador, no detiene procesos por si mismo.
4. Verificar contador singleton y UNIQUE de una sola columna `person.code`. El nuevo proceso valida ambos al iniciar; si faltan, no permanece listo. La migracion es idempotente pero el DDL no es transaccional. No eliminar contador/indice en rollback automatico.
5. Configurar `VPS_KNOWN_HOSTS` con la clave de host obtenida y verificada por un canal confiable, incluyendo `[host]:puerto` cuando corresponda. No aceptar ciegamente la salida de ssh-keyscan. El script rechaza hosts desconocidos o cambiados.
6. El VPS debe disponer de nvm/Node22, npm, PM2, curl, tar y OpenSSH, acceso al directorio de aplicacion y soporte de symlinks/rename Linux. El uploader admite hostname/IPv4 y rutas absolutas sin espacios.
7. Ensayar en Linux una instalacion fallida, arranque fallido, readiness fallida y cambio exitoso con PM2 real. QA local Windows usa junctions para emular los enlaces: no demuestra atomicidad Linux ni disponibilidad del VPS.

El uploader instala bajo `releases/<run-id>-<attempt>`, conserva releases anteriores y cambia `current` despues de instalar dependencias. `/readyz` debe devolver HTTP 200, `ready:true` y el release esperado; liveness por si sola no basta. En fallo se restaura la version anterior; el operador debe verificar tambien su disponibilidad. No hay poda automatica de releases.

`logs` y `src/tempFolder` se enlazan a `shared/` y se preservan en la primera transicion desde una carpeta legacy. Verificar disco, propietario y permisos antes del ensayo. `.env` y claves temporales usan modo 600. El uploader elimina la clave local, known_hosts temporal y paquete al terminar; no imprime valores.

## Reconciliacion de fallos parciales

- `logs/signature-email-audit-pending.jsonl`: el proveedor acepto el correo pero fallo el evento de auditoria. Usar requestId/tenant/provider/messageId para comprobar el estado y evento existentes, y registrar una reconciliacion idempotente mediante el proceso operativo autorizado. No reenviar correo ni invalidar un token por este marcador. Aceptacion del proveedor no demuestra entrega al destinatario.
- `logs/storage-cleanup-pending.jsonl`: verificar bucket/key exactos y ausencia de referencias en `files`/`profile_px` antes de reintentar borrar. `persistence_unknown_verify_before_delete` significa resultado SQL incierto: no es permiso para borrar. Si existe una referencia confirmada, conservar el objeto y cerrar la incidencia operativa.
- Conservar copia del diario y evidencia de reconciliacion; retirar solo entradas ya resueltas. No almacenar enlaces de firma, contenido clinico o credenciales en reportes. No existe worker automatico de reconciliacion en esta entrega.
- Alertar sobre `SIGNATURE_EMAIL_AUDIT_PENDING`, `STORAGE_CLEANUP_PENDING` y fallos de escritura del diario. Si el disco no permite escribir, el marcador en log es la unica evidencia de fallback; revisar capacidad y permisos.

## Cambios de contrato que requieren aceptacion

- Recetas emitidas nuevas usan `patient_identity_source=issued_snapshot`. Borradores usan `current_record`; historicos sin snapshot, `legacy_current_record`. Estos ultimos conservan compatibilidad y no pretenden reconstruir una identidad historica desconocida.
- Lecturas de historia exigen tambien `clinical_history.view_sensitive`. Revisar roles legitimos en staging; no conceder permisos globales de forma automatica.
- Directorio de doctores exige permisos de recetas. Inventario global de buckets exige super_admin.
- Si `SUPER_ADMIN_SESSION_REAUTH_REQUIRED=true`, cerrar una sesion ajena responde 403 `SESSION_REAUTH_REQUIRED`. Falta un flujo de step-up verificable para autorizar esa accion; no desactivar el flag como arreglo automatico.
- Los errores SQL inesperados devuelven mensaje funcional y `data.reference`, sin SQL/valores/stack. Duplicados y referencias FK devuelven 409.
- Limpieza de rate buckets: hasta 1000 vencidos/minuto por instancia activa del limiter; no borra cuotas vigentes, depende de trafico y requiere observar crecimiento para dimensionar retencion.

## QA SQL aislada

El operador `scripts/qa/issues-mysql-regression.js` exige `ISSUES_QA_ISOLATED=1` y `ISSUES_QA_PORT` distinto de 3306. Solo conecta a loopback, crea una base `qa_issues_*` nueva y la elimina al terminar. Necesita un servidor MySQL desechable y usuario root de QA sin password; nunca apuntarlo al servidor habitual. Prueba cuotas concurrentes, codigos, snapshots de recetas, agenda request_id, retencion y readiness. No forma parte de CI sin configurar dicho servidor aislado.
